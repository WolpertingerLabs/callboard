## Implementation checkpoint (2026-09-06)

This is an implemented, reviewed preview, **not a claim that every release gate below has passed**.

- Implemented independent `@wolpertingerlabs/computer-use` 0.1.0 library, public TypeScript contracts, build/tests/README/license and standalone deny-by-default stdio MCP executable. Callboard's publication includes the built package; the independent tarball installs outside the workspace.
- Shared service owns authorization, owner/actor identity, generation-bound exclusive leases, bounded queues/action timeouts, session TTL, takeover/resume, stop/revoke and action events. Callboard supplies live metadata policy and short-lived human grants. Grants/screenshots are not restored after restart. Events are currently a bounded **in-memory** timeline, not a durable/compliance audit store.
- Browser driver uses public Playwright APIs directly, not `@playwright/mcp`: a smaller fixed coordinate-action surface lets the authoritative service own the persistent context and same screenshot viewer without exposing upstream evaluate/run-code. Profiles are disposable and isolated per session; browser binaries are never downloaded automatically. Operators can select an already provisioned compatible Chromium with `CALLBOARD_BROWSER_EXECUTABLE=/absolute/path`; the model cannot choose this executable. Browser websockets/downloads are blocked in this initial driver; no DOM/tab-management/file-transfer tool surface yet.
- A real native **Linux X11** driver uses fixed-argument xdotool/ImageMagick commands with explicit platform/architecture/display/dependency probes and an exclusive per-display lock. This is an initial reference implementation, **not user approval of Linux-first** and not qualification of the user's target. Unsupported macOS/Windows/Wayland targets remain unavailable; no fallback desktop or remote viewer-machine control. Remote authenticated helper and out-of-process crash supervisor are outstanding.
- All five engines register the neutral computer tool bundle. Every host handler uses an actual standard MCP client connection to the one package service. Claude/Codex/OpenCode ACP use their existing outer MCP registration; Cline/pi use custom-tool adapters around that MCP client. Cline's prior image placeholder was replaced with actual model content; pi image preservation and native MCP cancellation have regression fixtures. This verifies harness/model-payload paths, **not live selected-model visual competence**.
- Fifth `computerControl` permission, legacy missing-field deny, child/job defaults deny, settings note, common chat viewer, explicit enable/approval, opt-in screenshot preview, human pointer/keyboard/takeover/resume/stop/revoke are implemented. Human endpoints require a signed-in session and same-origin mutation requests, not agent API-key credentials.
- Conservative first-release policy: browser requires Web Access allow; native desktop requires the other four axes allow because pixels cannot enforce narrower OS permissions. Under computer control **ask**, every model-requested GUI mutation requires an expiring, one-action human confirmation, answerable only by a signed-in session; under **allow** the agent acts unattended and each action is recorded in the server log. A human enables the target at both levels. There is **no unrestricted scripting endpoint**; hybrid app scripting must use existing separately authorized code/file paths. This is deliberately less autonomous than the eventual sensitive-action classifier design.
- **PRE-security-fix, unsandboxed evidence only:** real disposable Chromium smoke passed: navigate, retained form state, screenshot bytes, human edits and resume, separate-owner isolation, stop. Independent package suite: 25 passed, zero skips on the available cached Chromium executable. No user's applications/projects were manipulated.

Those gates, target-OS choice, native emergency stop/supervision, model qualification, cross-machine helper if needed, and durable audit retention remain open. ## 1. Recommended outcome

Deliver managed, persistent **interactive browser AND full desktop environments**, not additional test scripts. Each has visible current state, screenshots, an action timeline, exclusive agent/human control, scoped approvals, and explicit enable, stop, revoke, and cleanup operations.

Create an extraction-ready `packages/computer-use/` service/library and standard MCP executable. Callboard supplies identity, permissions, approvals, persistence adapters and UI; the package imports nothing from Callboard. Support **all five current Callboard engines: Claude Code, Codex, Cline, pi, and OpenCode via ACP**. Preserve existing harness integrations, including Codex SDK; do not reinstate retired OpenRouter-as-engine. Use one standard MCP package through native clients where appropriate and explicit host bridges where required. Claude Agent SDK and Codex must also work directly with the standalone executable; pi requires an MCP extension/bridge outside Callboard too.

**Initial OS/deployment is unresolved, not user-approved Linux/Docker-first.** Choose and qualify at least one actual desktop target before implementation estimates are finalized. Both native-host and managed/isolated targets sit behind the same service/driver API; neither is silently substituted for the other. Full desktop means permitted GUI applications such as **Aseprite and Blender**, not only Chromium. Cross-engine support is a separate axis from cross-OS support: supporting all engines does not automatically require every OS at first release.

| Environment choice | Fit for intended work | Limits and qualification |
|---|---|---|
| Native desktop on the service host | Uses the user's installed Aseprite/Blender, project directories and GPU; strongest fit if “my desktop” is the goal | Shared OS input/display requires exclusive machine/session lease, local emergency stop, OS capture/input consent and sensitive-window privacy. Cannot promise per-path/network sandboxing from pixels. Stopping must not kill unrelated apps or discard unsaved work |
| Native desktop on another machine | Same personal-app workflow when Callboard backend is elsewhere | Separately installed authenticated helper is required in the first delivery if this is the selected use case, not automatically a later phase. Pairing, disconnection fencing and target identity are mandatory |
| Dedicated OS user/session or VM | Separates agent work from personal windows; can provide stronger filesystem/network controls | Provision applications and project transfers; GPU/3D acceleration, clipboard, display and render performance must be tested. A VM is not the same desktop as the user is already viewing |
| Linux X11 worker/container | Reproducible managed GUI and browser target; plausible optional CI/reference environment | Ubuntu 24.04 x86-64 is a candidate, not selected. Requires display stack, applications, graphics support and explicit mounts; Docker is optional infrastructure, not a package prerequisite. Software rendering may suit small scenes but is not promised usable Blender viewport performance |

Choose native mode when access to the existing apps/desktop is essential; choose managed mode when isolation and reproducibility matter more. Native Windows/macOS/Linux support each needs capture/input/backend qualification (Wayland differs from X11). Prefer the user's real target OS over implementing a Linux detour that does not satisfy the use case.
A viewer on another computer does not make that computer controllable. Tools act where the configured service/worker runs. Controlling a viewer's own machine requires a separately installed, paired, authenticated helper and explicit local consent.

- `shared/types/providers.ts`, `agents/factory.ts` and `adapters/acp/vendors.ts` confirm five routable kinds (`claude-code`, `codex`, `cline`, `pi`, `acp`) with **OpenCode the only shipped ACP preset**. Mock is test-only; old OpenRouter comments/files are not a supported engine.
- `shared/types/permissions.ts`: four current categories. New `computerControl` is the **fifth**, labelled **Browser & Computer Control**.
- `ToolPermissionPolicy.ts` resolves unknown/missing settings to ask. Codex has no per-call `canUseTool` callback; categorization alone cannot enforce the feature. `services/claude.ts` already has permission-request events and live metadata permission reads, but the new service must independently authorize.
- Four-category allow literals occur in `services/callboard-tools.ts` (child start), `agent-tools.ts`, `agent-executor.ts`, and `job-runner.ts`. Audit all, plus queue/import/fork/resume paths. Do not automatically append `computerControl: allow`.
- `frontend/src/utils/localStorage.ts` stores UI defaults; `PermissionSettings.tsx` is reusable across permission screens. Backend records use file-backed services; avoid introducing a database solely for this feature.
- `backend/src/index.ts` mounts authenticated API routes through `auth.ts`. New viewers, screenshots, events and upgrades must follow that boundary; an unprotected worker port is not acceptable.

## 4. Package boundaries and public contracts

Proposed layout (new files, not yet created):

```
packages/computer-use/
  package.json, tsconfig.json, README.md, LICENSE
  src/index.ts                 # stable library exports, no startup side effects
  src/contracts.ts             # versioned DTOs and validated action unions
  src/service.ts               # sole authorization/lifecycle entry point
  src/policy.ts, grants.ts, leases.ts, scheduler.ts
  src/drivers/{types,browser-mcp,desktop-mcp}.ts
  src/workers/{supervisor,protocol}.ts
  src/mcp/{server,tools,cli}.ts # standard MCP stdio executable
  src/client/{connection,discovery}.ts # reusable MCP client for non-native hosts
  src/control/{router,events}.ts
  src/storage/{types,file-store}.ts
  test/{unit,contract,integration}/
  examples/{codex,claude-agent-sdk,cline,pi,opencode,standalone}/
  runtime/                     # recipes only for explicitly qualified environments
```

Optional `packages/computer-use-viewer/`: React peer dependency, transport-agnostic viewer/controller components, own build/tests/README; no Callboard stores, routes or CSS tokens. Callboard can initially supply styling around these components.

Public API sketch (contract intent, not implementation):

- `createComputerUseService({drivers, authorizer, approvalBroker, store, clock, auditSink, limits})`.
- `Principal`: trusted subject, host/tenant identifier, conversation and actor identifiers. Bound by host adapter/authentication, **never accepted as self-asserted tool arguments**.
- `EnvironmentSpec`: kind `browser | desktop`, immutable target/helper ID, isolation mode, profile ID, egress policy, mounted roots, allowed applications and capability ceiling.
- `Driver`: `probe`, `create`, `observe`, `execute`, `cancel`, `close`, `health`; capability-discriminated actions; all async operations receive abort signal/deadline. Driver IDs/paths are operator configuration, not arbitrary agent-selected endpoints.
- `Authorizer.evaluate(principal, request, currentPolicyVersion)` returns deny, bounded grant, or approval-required. Host cannot disable package-level scope/expiry/lease checks. Policy failure/unavailability denies execution.
- `ApprovalBroker.request(scope, actionDigest?, expiresAt)` plus authenticated out-of-band resolution. Standalone default is deny until configured; ask without a connected approver returns `approval_required`, not implicit approval or an indefinite hanging tool call.
- `Session`: opaque ID, owner, environment ID, state, capabilities, generation, controller lease, last activity. `Grant`: subject/session/target/kind/capabilities, roots/origins/app constraints, expiry, policy version, revocation epoch; no browser-to-desktop widening.
- `Observation`: frame ID, generation, timestamp, dimensions/DPI, crop/coordinate transform, MIME image bytes and optional browser DOM/accessibility snapshot, URL/tab/window identity. References expire on navigation, takeover, resize or generation change.
- `ActionRequest`: request ID, session ID, expected generation/frame, discriminated operation and bounded parameters. Results contain status, action ID, fresh observation where appropriate, and typed errors. Duplicate mutation IDs return the previous outcome; ambiguous interrupted actions are not replayed.
- `Event`: monotonically ordered sequence, owner/session/target, lifecycle/action/approval/controller/error kind, sanitized summary, timestamp. Resync endpoint plus replay window; no screenshot bytes or typed secrets in general logs.

Expose stable MCP tools: `session_open`, `session_status`, `observe`, `browser_navigate`, `browser_tabs`, `browser_action`, `desktop_action`, `session_stop`. Browser operations prefer semantic targets, with bounded coordinate fallback; desktop supports screenshot, click/move/drag/scroll, keyboard/text, focus and allowed application launch. MCP tools may request access or yield control, but may not mint grants, choose principals, force-release human control, or approve themselves. Human enable/revoke/takeover are authenticated control-plane operations.

Standalone executable: standard stdio MCP with explicit config and operator identity, same checks as embedded mode; stdout exclusively protocol, stderr sanitized diagnostics. Optional HTTP deployment uses authenticated Streamable HTTP with TLS and vetted auth middleware, Origin/Host checks and per-principal sessions; not an unauthenticated port. Keep viewer/events separate from MCP so clients need no UI extension. Provide direct Codex and Claude SDK examples plus Cline/OpenCode registration and a pi bridge example, using pinned executable paths. Document native versus bridged integration honestly; never require importing Callboard.

### Revised architecture: one execution implementation, actual MCP on every engine path

```
Claude / Codex / OpenCode native MCP clients -> package MCP server
Cline (if bridged) / pi custom tools -> MCP client -> same package MCP server
package MCP server -> authoritative service -> browser/desktop driver
Callboard human viewer -> authenticated control API -> same authoritative service
```

1. Add a host-owned `ComputerUseMcpBinding` descriptor carrying connection factory/config, immutable owner/target scope, versioned discovery manifest and disposal/turn-fencing hooks. Keep it separate from opaque legacy `options.mcpServers` shapes; adapters explicitly accept it instead of silently skipping an unfamiliar handle.
2. Native paths receive a stdio relay/connection to the **same long-lived service**, not a new independent desktop service per tool process. Claude in-process MCP is acceptable only if it adapts the package server, not a parallel implementation. A standard MCP `InMemoryTransport` pair is an optional embedding optimization; still exercise real MCP initialize/list/call semantics. Existing unrelated Callboard tool adapters need not be rewritten.
3. pi and optional Cline bridge use the package's reusable MCP client. `tools/list` -> bounded validated descriptors -> harness custom-tools; calls map back to MCP `tools/call`. The bridge does only transport, names/schema, result representation, cancellation and diagnostics. **No policy or driver execution duplication.** Server authorization remains authoritative even if harness approvals are absent/auto-approved.
4. Use a fixed small initial manifest; no reliance on dynamic tool-list refresh, MCP Apps, sampling, elicitation or tasks support. Discover before starting a model turn and fail explicitly on missing tools. Unknown upstream tools/schema changes fail closed; registration never widens authorization. Reconnect refreshes manifest/version and maintains an explicit alias map.
5. Bind identity at trusted connection creation. Reusing a connection across unrelated owners is prohibited. Resident Cline tools resolve the current authorized turn binding, not old captured grants. Calls without an attributable turn cannot control an environment. Engine switching within the same chat releases the old controller, creates a new connection/lease, checks model readiness and requires a fresh observation; sharing a chat ID does not allow two simultaneous controllers.
6. Package public interfaces remain Callboard-free. Any harness-specific pi/Cline glue belongs in Callboard adapters or separately exported optional adapter modules with peer dependencies—not mandatory SDK dependencies of the core service. Standalone users configure an authorizer/control approver; the package never trusts model-supplied identities.
7. Permission settings remain visible for configuration, but unsupported/unqualified engine/model/target combinations show a clear reason and disable agent Enable/control. Human stop/revoke remain available. Never show a working green control permission whose actions bypass checks or whose screenshots only reach the human UI.

**Scope/effort change:** extra MCP client/discovery plumbing for pi; Cline multimodal normalization and resident-session rebinding; ACP name/capability/provider qualification and child-session ambiguity; five real harness integration suites plus model-route probes. These are substantive additions, not five config entries. Reuse existing harnesses; a failed gate may require a reviewed upstream fix/version constraint and must not be hidden behind a compatibility claim.

## 5. Permission semantics, persistence and migration

Add `computerControl: PermissionLevel` and a shared runtime normalizer. Recommended new/missing field default: **deny**, including legacy chats, local defaults, agents, queued messages, frozen job runs and imported records. Preserve other four categories unchanged. Invalid incoming values fail validation; legacy missing values normalize to deny. Existing clients omitting the field during a partial update must preserve the stored value, not erase it. Explicit full replacement normalizes safely. Use a versioned, idempotent file migration or read-normalization plus atomic write-on-update; never mass-grant on upgrade.

UI row: **Browser & Computer Control** with Allow / Ask / Deny. Short note directly under that row:

> Control a managed browser or desktop on the service host.

- **Deny:** no managed agent or viewer screenshots, DOM observations, input, session launch or access to cached frames. Redacted status and human stop/revoke remain available for safety. Cannot override deny by a tool-supplied approval flag.
- **Ask:** explicit human approval binds a session, target, browser/desktop kind, capabilities, limits and expiry, and **every model GUI mutation** is then confirmed one action at a time in the chat. Denial/timeout has no side effect.
- **Allow:** skips ordinary session approval and the per-action confirmation, only inside an operator-configured, enabled environment and scope. It does not enable a target on the agent's behalf, select the host desktop, import personal cookies or authorize all helpers. No configured target means configuration required.
- Child sessions inherit at most the parent's policy ceiling; default to no grant. They never inherit live credentials/control leases. Explicit delegation requires a separate grant and independent environment or exclusive lease handoff. Scheduled jobs require explicit scoped configuration; ask with no human present becomes a bounded approval wait or blocked step, never allow. Frozen definitions contain policy config, not reusable grants.
- Mid-session policy/target edits bump the authorization epoch and invalidate affected grants. Lowering permission applies immediately to all active adapters. Persist revocations before acknowledging success; storage failure fences the worker and reports failure.

Persistence: add shared computer-use settings/session/event DTOs and optional references in chat metadata (not raw browser state). Package `Store` persists versioned environment/session metadata and sanitized audit records in a separate data directory; profile secrets stay in owner-private worker storage, optionally encrypted using a host-supplied key provider. Never put cookies/tokens in chat JSON, exports, logs or model instructions. Live grants are not restored automatically after process restart. Existing profile data may survive an explicitly opted-in stop, but reopening requires fresh authorization.

### Interaction with the existing four categories

Authorization is an intersection, not a substitute:

- In confined environments, `webAccess` governs networking as well as explicit navigation: deny means no egress; ask needs a bounded network grant. Enforce at worker/proxy level, including redirects, subresources, WebSockets and private/loopback destinations. Browser URL checks alone are insufficient. Existing open pages must lose network access on network revocation in confined mode. Native mode cannot silently reinterpret this promise: if its target apps cannot be confined, reject a strict deny/ask-egress configuration or require an explicit compatible broader scope; never claim the permission row firewalls the whole personal desktop.
- `fileRead/fileWrite` govern explicit uploads/downloads, clipboard/file bridges and host mounts. No host home, SSH keys, browser profile, Docker socket or credentials by default. Use separate bounded transfer directories and confirmations. Worker-local scratch/profile writes are disclosed runtime infrastructure, not permission to edit host files.
- UI apps can themselves read/write/send data. For generic desktop control, do not promise path-aware enforcement from pixels. Enforce filesystem and network constraints through the worker environment; reject configurations whose promised restrictions cannot be enforced. Native host desktop mode must disclose broader effects and refuse incompatible strict confinement settings.
- Launching a configured GUI app does not require generic `codeExecution: allow`; arbitrary script/shell tools are excluded from the baseline control API. Aseprite Lua/CLI and Blender Python execution require the separate code-execution decision plus relevant file/network permissions (see §10A); a desktop/browser grant alone is insufficient. A desktop terminal can nevertheless execute code, so permitted apps/environment scope must account for that. App-name filtering alone is not a security boundary.

## 6. Lifecycle, ownership and reliable control

State machine: `disabled -> approval_pending -> starting -> ready(agent|human|none) -> stopping -> stopped`; failure transitions to `failed`, authorization loss to `revoked`. A stopped/revoked session cannot be revived by a delayed action or approval; a new session/generation is required.

Service is authoritative across model turns. Per-turn MCP handles attach to it; closing a handle releases its agent lease/cancels that turn's pending operations but need not destroy a healthy explicitly retained environment. Abort/stop-chat fences pending agent input. Archive/delete/logout/policy revoke and backend shutdown have explicit cleanup hooks. A disconnected viewer does not grant control back to an agent.

- One action queue and one controller lease per environment; a desktop containing a browser shares the same lock domain. Separate browser contexts alone do not isolate shared host input. Proposed managed limits: one browser and one desktop per chat, two workers total per host, configurable after measurement. Native-host default: one controller across all controlled apps/displays in that OS session, not one per chat; app-window scoping does not create independent keyboards.
- Human takeover atomically increments the control epoch, blocks new agent input, cancels queued actions, aborts/fences in-flight input and releases held keys/buttons before the UI enables human input. Only the authenticated human can return control. Agent must observe again before acting.
- Validate authorization at enqueue, dequeue and immediately before dispatch; validate epoch again before delivering screenshots/results. Capture is an authorized action. In-flight effects cannot always be undone: report uncertain outcomes and never claim rollback. Kill/fence unresponsive isolated workers; native helper cancellation must fail closed where possible and visibly report limits.
- Stop/revoke have a priority path independent of the action queue. Stop terminates current execution and closes the control session (managed workers may be terminated; native mode detaches/releases input without killing pre-existing apps or discarding unsaved documents); revoke also invalidates grants/tokens and viewer streams/caches. Both are idempotent.
- Proposed limits: 30-second action timeout (explicit bounded longer navigation), queue 16, 15-minute idle expiry, 2-hour maximum session grant, 1280x800 default frame, 2 fps preview maximum and size/CPU/memory/PID/disk caps. Tune from measurement; screenshots to the model on demand/action checkpoints, not every preview frame.
- Worker/helper supervisor owns only resources it created; managed process groups/containers may be terminated, while native existing app processes must not be indiscriminately killed; heartbeat watchdog closes orphaned sessions if backend disappears. Restart reconciles manifest/PIDs against authenticated worker identity, never blindly kills arbitrary recorded PIDs. Recovered state is stopped/untrusted until checked; no action auto-replay. Profile TTL/retention separate from live worker TTL.

## 7. UI and control protocol

Settings: permission row/note plus environment setup cards showing host/helper name, OS support, prerequisites, isolation, browser versus desktop scope, profiles, retention and resource limits. Setup diagnoses only; it does not silently install browsers, obtain OS permissions or launch sessions.

Chat side panel: target-machine banner, browser tabs/URL or desktop window/display, timestamped live frames, controller indicator, action timeline, approval cards, Enable, Take over, Return to agent, Stop and Revoke. Display stale/disconnected state prominently. Never embed arbitrary target pages inside Callboard's origin; render pixels and escaped metadata. Human typing/keyboard shortcuts must stay inside the focused viewer. Coordinate mapping includes DPI/letterboxing and rejects stale frames.

Proposed authenticated API under `/api/computer-use`: environment list/probe, session create/status, approvals resolve, controller acquire/release, stop/revoke, authorized frame retrieval and sequenced event stream. Human input uses bounded POST or authenticated WebSocket messages with lease/generation IDs. Initial screenshot-based viewer is sufficient if human input is genuinely interactive; evaluate a dedicated video transport later, not raw exposed VNC/CDP. Remote helper phase: local installation, short-lived one-time pairing, explicit machine identity, outbound mutually authenticated connection preferred, per-device credentials with rotation/revocation, local visible enabled indicator and emergency stop. No public listener/control port by default. Credentials are bound to the helper/owner/target and are not included in tool prompts.

## 8. Security limitations and confirmations

This permission governs managed tools, **not unrestricted shell execution**. An agent with the same OS account and arbitrary execution may bypass tools, read local process credentials or run other automation. Strong isolation requires separating the agent's shell environment from the control service/worker authority, not hiding a tool name.

Use least-privilege workers with no host mounts by default, isolated profiles and bounded egress; containers alone are not equivalent to VMs. Do not disable Chromium sandboxing merely to make deployment work. Treat page text, screen text, accessibility trees, downloads and tool results as untrusted data that cannot expand permissions.

Require separate human confirmation for purchases, sending messages/files, credential entry, destructive actions and other irreversible changes. Bind confirmations to target/action digest and current generation, short expiry and one use. Pixel-based sensitive-action detection cannot be complete: when intent cannot be classified safely, hand control to a human rather than claim automatic protection. Login should use takeover with agent observations paused; clear cached frames and re-observe after return. Authenticated sessions remain sensitive after login, and actions can act as that user.

Screenshots may contain secrets. Default ephemeral capture, no automatic timeline/transcript image archive, no sensitive text in audit logs, bounded image dimensions/retention; make sending screenshots to the chosen model explicit in setup/approval. Model transcripts may retain already-delivered images: revocation prevents future access, not retroactive deletion from provider context. Redaction is best effort, not a guarantee. Disable clipboard sync/file transfer by default.

### Hybrid construction without permission bypass

Aseprite provides Lua scripting and CLI operations; Blender provides Python automation. These can do precise construction efficiently, followed by visible app inspection/refinement. ### Scenario B — Blender model and inspection

Preconditions: installed Blender version with qualified Python/API/export support; project/output roots; display capture/input and functioning 3D viewport. Test chosen GPU/driver/API and render engine on actual hardware. **Exact minimum graphics requirements were not established in this research** (Blender requirements/manual web pages returned access errors); recheck official requirements for the selected Blender version during provisioning. Do not promise GPU passthrough, hardware rendering or acceptable software-render performance from a generic container/VM.

1. Open a disposable scene and construct/edit a small low-poly object (for example a stylized crate with bevels/materials), with camera/light. Python can build precise geometry under approved code scope; keep the result visible in the controlled Blender session.
2. Model receives actual viewport screenshots, orbits/zooms/selects through UI, identifies a visible feature and refines it. Inspect a simple render; CPU rendering may be accepted if measured usable, with no assumption that it also solves viewport graphics.
3. Human takes over to change a material or object transform; return control and re-observe before continuing. The agent must preserve that change.
4. Save `.blend` and proposed `.glb` (or another agreed format). Reopen `.blend` and validate object/material presence; reimport the interchange export in a disposable scene to check geometry and supported material/transform fidelity. Document expected format losses instead of demanding exact .blend equivalence.
5. Exercise cancellable bounded render jobs/status polling, revoke while render/input is pending, and confirm no unauthorized subsequent screenshots or inputs. Stop native control without killing unrelated Blender work.

Run both scenarios on each engine using capable configured models and the same reference task/target class. Review actual artifacts and application state; a model saying “done” is insufficient. Target-specific scripting reliability, visual reasoning and artistic results can vary. All-engine qualification is feasible in architecture but remains **unproven until these gates run on explicitly qualified targets**.
